LNURLcash: bearer assets with LUD-25

2026-08-10

introduction

i've spent a lot of time in the lnurl/luds spec repo, and one of the drafts i wrote there is LUD-25, "LNURLcash, Bearer assets" (open as PR #301). this post is about what it actually does, and about two small projects, lnurl-wallet and lnurl-mint, that implement it end to end.

the idea

an LUD-03 withdraw link is redeemable by anyone who holds a valid k1. that's already a bearer property, LNURLcash just takes it seriously: instead of treating k1 as a one-time ticket that gets exchanged for a BOLT-11 invoice and thrown away, a service can credit a k1 with value and let it be the asset. it can be copied, printed, NFC-tapped, or handed to someone else exactly like a banknote, and it can be re-issued, merged, or split into change, all without the holder needing to be online.

the clever part is that this needs no new endpoint and no new encoding. a bearer note is nothing more than a normal lnurlw:// withdraw link:

lnurlw://mint.example/withdraw?k1=<secret>&amount=<msat>

a service that implements LNURLcash is still speaking plain LUD-03. a wallet that has never heard of LNURLcash still sees an ordinary withdraw link, and can cash it straight out to a BOLT-11 invoice like it always could. the extension is fully optional and backward-compatible in both directions.

minting

notes come into existence through an ordinary LUD-06 payRequest. a payLink can advertise a withdrawLink pointing at its own withdraw endpoint, one that recognizes the payment preimages of invoices it issued. pay the invoice, and the preimage you get back is a valid k1 at that endpoint, credited with the amount you paid (minus an optional, advertised mint fee). no separate minting call, the payment itself is the mint.

redeeming: melt, rotate, split, merge

everything happens against the callback url from the withdraw JSON. the informational GET on the note's own LNURL is purely read-only and never burns anything, which is what keeps legacy wallets safe. what the callback does depends on which parameters show up together:

  • k1 + pr — melt: plain LUD-03 behaviour, the note is burned and the invoice gets paid
  • k1 alone — rotate: the note is burned and a fresh one of the same value replaces it
  • k1 + amount — split: burned, two new notes come back, one for amount, one for the remainder
  • several k1s — merge: all burned, one note worth their sum comes back

melting is asynchronous the way LUD-03 already is: the service marks the note pending, returns OK, and only burns it once the outgoing payment actually settles, restoring it otherwise. any other operation on a pending note is rejected until that resolves.

offline circulation and verification

because a note is self-contained, holders can hand it to each other with zero connectivity to the issuing service, an NFC tap or a QR code is enough. the catch is that a bare (k1, amount) pair proves nothing on its own, a forged secret with an inflated amount looks identical to a real note until someone actually asks the service. LUD-25 closes that gap with an optional signature: the service publishes a mintPubkey and signs each freshly rotated/split/merged note the same way LUD-13 already signs its auth seed phrase, via the node's own signmessage. a recipient can then verify issuer and amount offline, before deciding whether to trust the person handing it over. it still can't prove a note hasn't already been spent elsewhere, that only an online rotate settles for good.

lnurl-wallet

lnurl-wallet is a serverless reference wallet for LNURLcash notes, a single static page with no backend and no accounts, deployed to GitHub Pages and hosted at dni.github.io/lnurl-wallet. everything lives AES-256-GCM encrypted in local storage, keyed off a linking key derived from a BIP39 seed phrase the same way lnurl_server derives its LUD-05 identities. it talks directly to whatever mint issued a note, follows the spec's security guidance to the letter, rotating received and freshly minted notes immediately rather than sitting on a secret the previous holder (or the mint's own node) also saw, and shows a "signed" badge when a note's signature checks out against a known mintPubkey. built with Vite, SolidJS, and @scure/@noble.

lnurl-mint

lnurl-mint is the other half, a minimal FastAPI backend that implements the spec against a real Lightning node (lnd or cln). it exposes the payRequest/withdrawRequest pair, mint fees, LUD-21 verify, offline verification via the node's own signing RPC, and Tor support that swaps the advertised base URL for a wallet actually connecting over an onion address. it only ever stores sha256(k1) for outstanding notes, never the secret itself, and disables per-request access logging entirely so a bearer secret never ends up sitting in a log file. it's the sibling of lnurl_server with everything stripped away except the mint.

the two projects track the spec closely enough to interoperate, down to tolerating a byte-order quirk in how lnurl-mint currently emits recoverable signatures, exactly the kind of small real-world mismatch you only find by actually running two independent implementations against each other.
