bip340-batch-verify: 128-bit randomizers are sound, and the bound is tight

2026-10-30

introduction

yesterday i wrote about proving BIP340 batch verification in taproot-lean, and said the hash-derived part was still work in progress. it's done now. i cleaned it up and pulled it out into its own repo, bip340-batch-verify, so people who only care about this one question don't have to build all of taproot-lean (BIP341, MuSig2, DLCs, bech32m) to check it.

the short version: BIP340 batch verification with 128-bit randomizers derived deterministically from the batch is sound, the attacker wins with probability at most (q + ℓ)/2^128, and the q term can't be improved. all of it machine-checked in Lean 4 with Mathlib and VCVio, no sorry.

why this matters right now

sipa/bips#219 and sipa/bips#222 propose shrinking BIP340's batch-verification randomizers from 256 to 128 bits. that makes batch verification in libsecp256k1 up to about 9% faster. the pen-and-paper argument for it treats the randomizers as independent uniform values. but that's not what implementations do. they hash them out of the batch, and with incremental derivation, like libsecp256k1's batch API, the attacker gets to pick later entries after seeing earlier randomizers. that's exactly the gap i wanted closed.

as a reminder, batch verification checks one equation instead of u separate ones:

Σ aᵢ · (sᵢ·G - Rᵢ - eᵢ·Pᵢ) = 0      with a₁ = 1

results

each of these holds for every choice of the challenge hash. q is the number of random oracle queries the attacker makes, ℓ the maximum batch size, b the randomizer width.

  • independent uniform randomizers (batchVerify_sound_bits): an invalid signature is caught except with probability 2^-b. this is the textbook case.
  • whole-batch derivation, as written in the BIP340 text (batch_indexed_sound): randomizer aᵢ is the hash of the whole batch plus i. an invalid batch is accepted with probability at most (q + ℓ)/2^b.
  • incremental derivation, as in libsecp256k1 (batch_incremental_sound): aᵢ hashes the first i entries. the same bound, (q + ℓ)/2^b, even though the attacker adapts to the randomizers it has already seen.
  • on secp256k1 with b = 128 (secp256k1_batch_indexed_sound, secp256k1_batch_incremental_sound): (q + ℓ)/2^128, with no extra hypothesis about the curve.
  • lower bound, for both derivations (batch_indexed_grind, batch_incremental_grind): an explicit attacker reaches 1 - (1 - 2^-b)^q ≈ q/2^b, so the q term is tight.

what that means in practice: 128-bit randomizers are fine, and the only price of deriving them deterministically is offline grinding at one hash per attempt. about 2^64 hashes buy you a 2^-64 chance of getting an invalid batch through. nothing cheaper than that exists, and the proof says so.

the grinding attack

the lower bound is a nice little attack. take one valid signature (pk, m, r, s) and build the batch

[(pk, m, r, s - δ), (pk, m, r, s + δ)]

both signatures are invalid, but their errors are -δ·G and +δ·G. with a₁ = 1 the batch passes exactly when the second randomizer is 1. so the attacker just hashes these batches for δ = 1, …, q and waits. each try is an independent 2^-b shot.

the same attacker works against incremental derivation too, and that's proven as well. for a two-signature batch the second randomizer hashes the first two entries, which is the whole batch, so both derivations look the same to it. in Lean the attack is stated once, as batch_grind, for any derivation where the candidate batches hash to different oracle inputs. both lower bounds follow from it in one line each.

how the upper bound is proven

whole-batch derivation is the easy case: one fresh oracle answer completes at most one batch, so each query is bad with probability at most 1/2^b.

incremental derivation is where it gets interesting. cut a winning batch after its last invalid signature. that prefix still passes, and its equation only involves randomizers of its own prefixes. whichever of those is answered last has to hit the one value that solves the equation. the problem is that one fresh answer can complete many prefixes at once, all the cached extensions of the prefix that was just queried. so the naive "one bad value per query" argument breaks.

the fix is a small, general lemma, prEvent_bad_le: a bad-event bound for lazily sampled random oracles with a potential, the number of cached prefixes still waiting to be completed. one query may be charged for several bad values, as long as earlier queries prepaid for them. each cached prefix is completed only once, so in total it's still one bad value per query. with potential zero it's the usual bound. i think that lemma is useful beyond this repo, for any random oracle argument where answers can complete more than one thing at once.

trust base

  • the seed hash and CSPRNG are idealized as a random oracle. the first randomizer is fixed to 1, like in BIP340.
  • the challenge hash is an arbitrary function, nothing about SHA-256 is assumed.
  • the generic theorems assume every point satisfies n·P = 0. for secp256k1 that's proven (Secp256k1.card_eq_n), and it turned out to need no point-counting algorithm at all, see below.
  • secp256k1 itself is y² = x³ + 7 as a Mathlib WeierstrassCurve with Mathlib's proven group law. p and n are proven prime with kernel-checked Pratt certificates, generated by a small PARI/GP script.

lake build prints #print axioms for every main result. all of them, the secp256k1 versions included, use only Lean's standard axioms (propext, Classical.choice, Quot.sound). there is no native_decide anywhere, so nothing trusts Lean's compiler.

secp256k1 has exactly n points

the hypothesis n·P = 0 for every point P sounded like it needed real point counting. it doesn't. a short argument is enough:

  • a point is determined by its x-coordinate and the parity of its y-coordinate, so there are at most 2p + 1 points.
  • G has order n, so n divides the number of points. since 3n > 2p + 1, there are either n or 2n points.
  • no point has y = 0, because -7 is not a cube mod p. so no point has order 2, and by Cauchy's theorem the number of points is odd. that leaves n.

with that, the secp256k1 theorems drop the hypothesis entirely.

n·G = 0 without native_decide

the one computation left, n·G = 0, used to run through native_decide, which trusts Lean's compiler. letting the kernel run Mathlib's group law directly would mean field inversions on 256-bit numbers, which is far too slow. instead a small script computes the double-and-add chain for (n - 1)·G and writes down the slope of every step, 448 of them. the kernel then only checks each slope, with additions and multiplications mod p, and Lean proves that every checked step is Mathlib's addition. the chain ends at -G, so n·G = 0. the same idea as the Pratt certificates for p and n: the hard work happens outside, and the kernel only checks the answer.

try it

git clone https://github.com/dni/bip340-batch-verify
cd bip340-batch-verify
lake exe cache get
lake build

if it builds, every proof checked. be patient though: VCVio has no prebuilt cache, so the first build can take an hour or more. on machines with little memory use LEAN_NUM_THREADS=1 lake build.
