taproot-lean: proving BIP340 batch verification

2026-10-29

introduction

LNURLcash notes are taproot output keys now, and a mint spends a lot of its time checking schnorr signatures. so i wanted to know, not just believe, that the cryptography underneath does what the BIPs say. taproot-lean is my attempt at that: machine-checked proofs in Lean 4, with Mathlib and VCVio, about BIP340 schnorr, BIP341 taproot, MuSig2, bech32m and DLCs.

what's in there

the proofs work over a concrete secp256k1 curve, built from Mathlib's elliptic curve group law, not over some abstract group. the primes p and n are proven prime inside Lean. hashes are modelled as arbitrary functions, so nothing about SHA-256 is assumed, and where a result needs collision resistance it is an explicit hypothesis.

most of it is correctness (sign then verify works, MuSig2 aggregation works, a DLC adaptor completes with the attestation), plus a few results about malicious inputs: non-malleability, special soundness (two signatures with the same r leak the key, so nonce reuse is fatal), script-tree binding, and an EUF-CMA reduction for BIP340 in the random oracle model.

why batch verify

BIP340 lets you check many signatures at once. instead of u separate checks you check one equation:

Σ aᵢ · (sᵢ·G - Rᵢ - eᵢ·Pᵢ) = 0      with a₁ = 1

that is a lot faster, but it's also the spot where a mistake is easy to make. if the coefficients aᵢ are predictable, an attacker can craft two invalid signatures whose errors cancel out, and the batch passes. so the question is: how random do the coefficients have to be, and does it still hold when they come from a hash of the batch, which the attacker chooses?

what's proven so far

in Taproot/BIP340Props.lean:

  • batchVerify_of_valid: a batch of valid signatures always passes, for every choice of coefficients.
  • batchVerify_sound: if one signature is invalid, then once the other coefficients are fixed, at most one value of its coefficient lets the batch pass. a random coefficient catches it except with probability 1/n.
  • batchVerify_sound_single: a single invalid signature with a nonzero coefficient, like BIP340's fixed a₁ = 1, is always caught.
  • batchVerify_sound_bits (new): the same with b-bit coefficients as long as 2^b ≤ n. so 128-bit coefficients, which is what implementations actually use because they are cheaper, catch a bad batch except with probability 2^-128.

current focus: hash-derived coefficients

the results above assume the coefficients are truly random and independent of the batch. real implementations don't work like that. libsecp256k1's batch verification API derives them deterministically and incrementally: aᵢ is a hash of the first i entries. that means the coefficient is known as soon as those entries are, and the attacker can pick the later entries after seeing it.

that's what i'm working on right now, in a new file Taproot/BIP340Batch.lean. it models exactly that game in VCVio: the attacker gets access to a random oracle, outputs a batch, and the verifier derives the coefficients from the same oracle. the main theorem, batch_incremental_sound, says:

if the attacker makes at most q oracle queries and outputs batches of at most ℓ signatures, a batch containing an invalid signature passes with probability at most (q + ℓ) / 2^b, for every choice of the challenge hash.

the proof charges every win to one random oracle answer. take the last invalid entry j of a winning batch, then the prefix up to j already passes, and its equation only involves coefficients of prefixes of that batch. whichever of those is answered last has to hit the one value that solves the equation. the tricky part is that one fresh answer can complete many prefixes at once, all the cached extensions of the queried prefix. the naive "each query is bad with probability 1/2^b" argument doesn't work then.

so the file has a small general lemma, prEvent_bad_le, a bad-event bound for lazily sampled random oracles with a potential: the number of cached prefixes that are still waiting for a coefficient. one query may be charged for several bad values, as long as earlier queries prepaid for them. with potential zero it's the usual bound, and the batch result falls out of it.

there is no sorry in it, but it is still work in progress and not pushed yet. i want to clean up the proof and the statement before it lands.

limitations

  • batch verification assumes every point satisfies n·P = 0. that's true for secp256k1 (cofactor 1), but proving it needs point counting, which isn't done.
  • it's the random oracle model, and transactions are reduced to the signed message. byte encodings only show up in the test-vector files.
  • MuSig2, adaptor signatures and DLCs still have no security reductions, only correctness and robustness results.

why bother

tests tell you that the vectors pass. a proof tells you that no batch, chosen by anyone, slips through with more than the stated probability. for something like a mint that verifies other people's signatures with money on the line, i'd like to know which of the two i have. and Lean is surprisingly good company for that, it never lets you skip a step.
