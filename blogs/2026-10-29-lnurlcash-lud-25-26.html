LNURLcash: LUD-25 and LUD-26, and everything around it

2026-10-29

introduction

in august i wrote about LUD-25, bearer assets. back then a note was a k1 secret, a lnurlw:// link you could copy, print and hand over. a lot has happened since. the spec got reviewed hard, rewritten around taproot, split into two documents, and grew its own github org with mints, wallets, client libraries, hardware and a hosted service. this post is the update.

the PR status

everything still lives in one pull request on lnurl/luds: PR #301, "LUD-25/26: LNURLcash, programmable bearer notes". it is open and still a draft, but it is not a lonely draft anymore. it has two co-authors now, tbk (Thebora Kompanioni) and thecryptodonkey, and the review thread is the best part of the whole thing.

  • the TollGate folks described a real use case: captive-portal internet access on OpenWrt routers, where the guest has no internet and no wallet. a bearer note works there on plain LUD-03 already.
  • thecryptodonkey built an independent LUD-25 stack, a mint, a wallet library and a conformance suite with an adversarial mock mint, and came back with a list of gaps. burns are now explicitly permanent, there is a real security considerations section, mutation requests got a retry rule (a GET that already burned its input must not be answered as if it never happened), and comment became mandatory for minting, matching what lnurl-mint already did.
  • small spelling questions like "is withdrawLink https:// or lnurlw://" only show up once two independent implementations talk to each other. that's exactly why the conformance vectors exist.

two side PRs came out of this work too. #302 added a zero balance recommendation to LUD-03 and got merged in august. #312 is a small, independent proposal for POST callbacks: send the same parameters as a JSON body instead of query parameters, which matters once you carry signatures and witnesses around instead of a single k1.

LUD-25: unified taproot notes

the biggest change is what a note is. it is no longer "a k1 with a balance", it is a BIP-341 taproot output key Q, written cp1<Q>. the mint stores Q → value and nothing secret at all. a note is spent the same two ways a taproot output is spent on-chain:

  • key path, ck1<...>: a BIP-340 schnorr signature by Q
  • script path, cw1<...>: a leaf script, its control block and the witness it consumes

the old bearer note is still there, it's just the simplest script: OP_SHA256 <h> OP_EQUAL under the nothing-up-my-sleeve point, so there is no key path and the preimage is the secret. and because everything follows from h, a mint accepts 64 hex characters as a short form, so a wallet that knows nothing about taproot can still use notes with nothing but sha256. old k1 style links keep working.

the nice consequence: the mint verifies spends with bitcoin's own script rules, a spend is valid if consensus would accept it as input 0 of a canonical spend transaction. that makes the note programmable: timelocks, multi-party leaves, hashlocks, oracle conditions, all with one lookup, one verification rule and one certificate format. and the mint does not have to reimplement script, it can hand it to Bitcoin Core's libbitcoinkernel, which is what lnurlcash/kernel wraps.

offline verification stayed, but certificates are now schnorr too: the mint publishes a mintPubkey, ideally its node id, and signs the notes it hands out (c/c2 for split outputs). a recipient can check issuer and amount without being online.

LUD-26: derivation and Lightning Address

LUD-25 got long, so at the end of september i split the HD part out into LUD-26, "note derivation and Lightning Address". it answers the question every bearer wallet runs into: what happens when you lose the device?

  • seed & derivation. per-service accounts are derived hardened, reusing LUD-05's domain hashing under its own purpose (m/139'), then note keys are derived non-hardened from (P, chaincode) with BIP-341 style parity handling. account 0 is the wallet's own (0'/0 for notes, 0'/1 for change), accounts n ≥ 1 are shareable.
  • recovery. re-derive pk_0, pk_1, ... per branch and per known service, ask the mint with ?p=cp1<pk_i>, stop after a gap limit. exactly how on-chain HD wallets recover addresses. key-path notes come back from the seed alone, bearer and script notes still need their own backup.
  • watch-only export. cx1<P || chaincode> is basically an xpub for notes. you can give it to a point-of-sale terminal or a bookkeeping tool that should see notes but never spend them. one fresh account per party, never account 0.
  • Lightning Address auto-mint. register a cx1 against a username and the mint publishes a normal LUD-16 address. every payment to dni@mint.example gets minted to the next unused key, the wallet finds it the same way it recovers. you can receive bearer notes while offline.
  • internal transfer. a payee's payRequest metadata can carry one key of their cx1, so a wallet paying someone at the same mint just moves the note to that key instead of a round trip over lightning.

today's commit on the spec branch is a breaking one: "derivation leaks". the derivation got tightened so a leaked note key together with a cx1 can't reveal or link the private account. that's the kind of thing you only want to break while it's still a draft.

the lnurlcash org

around mid august the projects moved out of my personal account into github.com/lnurlcash, and it has grown quite a bit since:

  • lnurl-wallet, hosted at wallet.lnurlcash.com: the serverless reference wallet. by far the busiest repo. recently it got an address page, multiple lightning addresses per mint, internal transfers to a user or a cx1, a qrcode addon, and address recovery fixes. it also has addons for DLC style bets (dlc and betlocker).
  • lnurl-mint, hosted at mint.lnurlcash.com: the python reference mint. went through the "grand taproot unification", the new derivation, and dropped all the compatibility code.
  • lnurlcash-core: the money-critical logic in rust, with UniFFI bindings for kotlin and swift, released on crates.io. lnurl-mint-rust (a mint with a built-in LDK node, admin panel and cli), cln-mint (a Core Lightning plugin that runs a mint) and lnurl-wallet-native all sit on top of it.
  • client libraries: lnurlcash-kit (typescript), lnurlcash-py, lnurlcash-go and lnurlcash-kotlin.
  • lnurlcash-conformance: shared vectors, an adversarial mock mint and a runner, so every implementation is tested against the same thing.
  • kernel: a libbitcoinkernel wrapper for tapscript validation, as a python wheel and a rust crate.
  • hardware: lnurl-vault (vault.lnurlcash.com), an ESP32 T-Display S3 companion that generates secrets and stores notes, and lnurl-card, a credit-card-shaped ESP32 device with eInk, NFC, a keypad and no battery.
  • fun stuff: raffle (raffle.lnurlcash.com) generates printable raffle tickets that are notes, and lnurlcash-contracts-demo is a real-sats lab for receiver-locked notes and cancellation bonds.
  • awesome-lnurlcash collects implementations, tools and writing, including other people's.

oracle

once notes are tapscript, a bet is just a script. lnurlcash/oracle is a standalone, single-oracle Discreet Log Contract service: it announces events ahead of time and later attests to the outcome that actually happened. the wallet's betlocker addon locks a note against an announcement and redeems it with the attestation.

it deliberately knows nothing about mints or notes, it never touches funds, it only signs outcomes. there is a small admin page for announcing and resolving events, and a scheduler that creates hourly and daily "will BTC be above its current price" events and auto-resolves them from a price feed. it is a single named oracle and not trustless, the design doc says so up front.

run.lnurlcash.com

the newest piece is run.lnurlcash.com, hosted LNURLcash mints. each mint is an unmodified lnurl-mint-rust with its own lightning node, kept liquid with LSPS2 and synced from a shared electrs over Bitcoin Core. provisioning works like the lnbits.com SaaS: run never talks to the cluster, it commits manifests to a kubernetes config repo and Argo CD rolls them out.

right now it's a beta list. you sign up with nostr (NIP-07 signer, NIP-98 http auth), only your pubkey, a short note and a timestamp get stored, no cookies. approved members can provision a mint straight from the page.

what's next

get the PR into a shape where it can be merged, keep the conformance vectors and all implementations in lockstep with every breaking change, and get a few real mints running on run.lnurlcash.com. if you build something on LNURLcash, open an issue on awesome-lnurlcash or comment on the PR.
